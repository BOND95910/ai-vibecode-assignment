## 1) ความถูกต้อง — ตรวจไขว้ครบ 3 ชุดเทสต์ × 3 เว็บ

ชุดเทสต์ทั้งสามเขียนโดยแต่ละแบบเองจากโจทย์เดียวกัน (51 TC เหมือนกัน) จึงรันทุกชุดกับเว็บของทุกแบบ (ไม่ตั้ง `BUG_MODE`) ผ่าน docker compose ของเว็บนั้น ๆ พร้อมเว็บที่ไม่มี `TEST_MODE` อีกตัวสำหรับ TC-NFR-03 และพาธฐานข้อมูลจริงสำหรับ TC-NFR-04

| TC ที่ผ่าน (จาก 51) | เว็บ B | เว็บ A | เว็บ C |
|---|---|---|---|
| **ชุดเทสต์ B** | **51** | 49 | 45 |
| ชุดเทสต์ A | 48 | 51 | 48 (49 ใน 1 จาก 5 รอบ · ดูหัวข้อความไม่นิ่ง) |
| ชุดเทสต์ C | 33 | 39 | 51 |

ทุกชุดผ่าน 51/51 กับเว็บของตัวเอง (เส้นทแยง) ตามที่แต่ละแบบรายงาน รันซ้ำแล้วได้ตรงกันทั้งสามชุด

**อ่านตารางอย่างไร:** ตัวเลขนอกเส้นทแยงไม่ได้แปลว่า "เว็บผิดเท่านั้น" ให้ sub-agent จำแนกทุก TC ที่ล้มนอกเส้นทแยง (ไฟล์ [`judge-harness/triage-web-B.md`](judge-harness/triage-web-B.md) และ [`triage-web-AC.md`](judge-harness/triage-web-AC.md)) ผลคือ **ไม่พบกรณีที่เว็บใดละเมิดข้อความใน spec ตรง ๆ** ที่เหลือคือชุดเทสต์เข้มเกินสิ่งที่ spec เขียน (ผูกกับสถาปัตยกรรมของเว็บตัวเอง) หรือ spec กำกวม

| สาเหตุที่ล้ม | จำนวนบนเว็บ B (TC ไม่ซ้ำ) | บนเว็บ A (นับ TC×ชุด) | บนเว็บ C (นับ TC×ชุด) |
|---|---|---|---|
| ชุดเทสต์เข้มเกิน/ผูกสถาปัตยกรรม | 14 | 11 (ชุด C ทั้งหมด) | 6 |
| spec กำกวม | 5 | 2 | 2 |
| เว็บละเมิด spec ตรง ๆ | 0 | 0 | 0 |
| ไม่ทราบ | 0 | 1 (NFR-02 ชุด C) | 0 |

- ชุด C ล้มบนเว็บ A และ B มากสุด เพราะเทสต์อ้างสถาปัตยกรรมของเว็บ C เอง: อ่านค่าจาก query string ของหน้า (`?period=` `?filter=` `?event=`) ซึ่ง spec ไม่ได้กำหนด · อ่าน DOM ทันทีหลัง `goto` โดยไม่รอ fetch · เทียบ JSON ทั้งก้อนด้วย `toEqual` ทั้งที่เว็บส่งฟิลด์เพิ่มได้ · ดึงข้อความ PDF แบบ `(…) Tj` เท่านั้น
- ชุด A กับ B ล้มบนเว็บ C ที่ TC-NFR-04 เพราะเปิดฐานข้อมูลเป็น SQLite แต่เว็บ C เก็บเป็นไฟล์ JSON (spec เขียน "ตามชนิดฐานข้อมูลของกลุ่ม") ค้นไฟล์ JSON นั้นแล้วไม่พบค่าส่วนบุคคลตรง ๆ สักค่า (ตรวจ ณ ไฟล์หลังรัน ไม่ใช่ระหว่าง TC)
- ข้อกำกวมจริงของ spec มีจุดเดียวที่ทำให้ชุดหนึ่งล้มบนสองเว็บ: ข้อความของ `noti-item` ว่าห้ามมีเวลาต่อท้ายหรือไม่ (เว็บ B แยกเวลาออกนอก item; เว็บ A, C ใส่ไว้ใน item; ชุด B ตรวจข้อความตรงตัว)

**จุดอ่อนจริงของเว็บ B (งานหลัก)** ที่ชุดของคนอื่นเจอ — ไม่ผิดตัวอักษรของ spec แต่ถ้าผู้ตรวจอ่านเข้มกว่านี้จะเสียคะแนน:
1. มี `<p data-testid="thaid-error|fee-error|upload-error|action-error" hidden>` ว่างไว้ตลอด ขณะที่ TEST-PLAN เขียนว่า "ไม่มี" (เว็บ C ลบ element ทิ้ง) → ชุดที่นับ element (`toHaveCount(0)`) ล้ม 5 TC (AUTH-01 ทั้งชุด A และ C · FEE-01, UPLOAD-01, QUEUE-03 ชุด C)
2. `audit-case-no` ของ EXPORT/ADMIN_CHANGE เป็นช่องว่าง ไม่ใช่ `–`
3. PDF มีบรรทัด `docNo=… validUntil=…` ในไบต์ดิบ/metadata แต่ไม่ใช่ข้อความ `(…) Tj` แบบเปิดอ่านตรง ๆ · รายการร่างบนหน้าเรียงสวนกับ API · SQLite โหมด WAL ทำให้ mtime ของไฟล์หลักไม่ขยับทันที · reload หน้าหลังส่งแก้ไข

> ข้อจำกัดของตารางนี้ (ระดับหลักฐาน): การจำแนกสาเหตุมาจากการอ่านโค้ดและ log เท่านั้น ยังไม่ได้รันซ้ำหลังแก้เทสต์เพื่อยืนยัน (ระดับ "ชี้บรรทัด/เดินโค้ด" ไม่ใช่ "รันแล้ว") · ตัวชี้วัดยุติธรรมกว่าที่ควรทำต่อ: รันชุด C บนเว็บ A โดยแก้ให้ใช้ฟอร์ม+auto-wait แทน query string และ `innerText` ทันที ถ้าผ่านแสดงว่า 11 เซลล์นั้นเป็นปัญหาเทสต์ล้วน

## 4) ข้อค้นพบเรื่องกระบวนการ

1. **คอร์สตามตัวอักษรรันจบไม่ได้กับบัญชีที่มี (Claude 2 บัญชี ไม่มี Codex):** วางแผนได้ครบ 13 บล็อก แต่ 9 บล็อกไม่มีบัญชีรับ (cyolo และ review ต้องใช้ฝั่ง Codex) orchestrator หยุดถามผู้ใช้ (ข้อสรุปมาจาก `dry-run` ไม่ได้รันจริงเพื่อพิสูจน์) จึงเปลี่ยนเป็น yolo ล้วน
2. **คอร์สแปลงความยากเป็นโมเดล:** orchestrator ให้ความยาก 3–5 ทุกบล็อก จึงได้ Opus high/xhigh/max ทุกบล็อก ไม่มี Sonnet เลย
3. **โควตา 5 ชั่วโมง:** `yolo2` เต็มภายในประมาณ 40 นาที ตัวคุมหยุดแจกงานที่ 80% แต่บล็อกที่เริ่มไปแล้วไม่ถูกหยุด · `dagplan.py` ไม่มี resume แต่ `team.py run --resume` รันซ้ำเฉพาะบล็อกที่ล้มได้
4. **C ใช้ output น้อยที่สุด (0.48M) และได้ผลระดับเดียวกัน:** พรอมต์เดียว เขียนเว็บ เทสต์ และสคริปต์ BUG_MODE เอง วนแก้ตามผล · C เขียนแผน DAG เป็น Mermaid (`reports/PLAN-DAG.md`) แต่เป็นการสรุปการแบ่งงานที่ทำจริงหลังเสร็จ ไม่มี Gantt ไม่มีแผนเทียบจริง ไม่มี agent-team (เพราะ `dag-planner`/`agent-team` ไม่มีบนเครื่องนี้) ส่วน A และ B ให้อาร์ติแฟกต์เหล่านั้นครบ
5. **รายงานที่ agent รายงานเองเชื่อได้บางส่วน แต่ไม่พอเป็นหลักฐานเดียว:** ทั้ง B และ C รายงาน 51/51 และ 12/12 ซึ่งตรวจซ้ำแล้วตรงทั้งคู่บนชุดเทสต์ของตัวเอง แต่ "ผ่าน 51/51" วัดเฉพาะการตีความของชุดเทสต์ตัวเอง การตรวจไขว้เปิดจุดที่ซ่อนอยู่ (ตารางข้อ 1)
6. **ตัวตรวจชุดเดียวเอนเอียง:** รอบแรกใช้ชุดของ A ตัดสินทั้งสามแบบ ได้ A 51 / B 47 / C 48 ซึ่งดูเหมือน A ชนะ พอตรวจไขว้ครบ 3×3 ภาพเปลี่ยน: ชุดเทสต์ของแต่ละแบบผ่านเว็บตัวเองเต็ม และไม่มีเว็บใดละเมิด spec ตรง ๆ ตัวเลข 47/48 ในรอบแรกมาจากข้อผิดพลาดของตัวตรวจ (ตั้งพาธฐานข้อมูลผิด) บวกการตีความต่าง

- โมเดลต่างกัน (A Sonnet, B/C Opus) · บัญชีและโควตาต่างกัน · สิ่งรบกวนต่างกัน
- การจำแนกสาเหตุของ TC ที่ล้มข้ามชุดมาจากการอ่านโค้ด/log ไม่ได้รันยืนยัน
- ชุดเทสต์ทั้งสามเขียนโดย agent ของแต่ละแบบเอง ไม่มีชุดกลางที่เป็นกลางจริง (ชุดของ TA ยังเป็นแค่ TEST-PLAN ในรูปการ์ด)
- ไม่มีราคาตามลิสต์ของ A

## ความไม่นิ่งของผลที่เจอ (ยังไม่ได้แก้ข้อสงสัย)

- **ชุด A บนเว็บ C**: รัน 5 ครั้ง (1 ครั้งจากเซสชันก่อนหน้า + 4 ครั้งในรอบตรวจไขว้) ได้ 48, 49, 48, 47, 48 ผ่านตามลำดับเวลา (ล้มคงที่: TC-NFR-04 ผูก SQLite, TC-WORKFLOW-06 reload หลังส่งแก้ไข) ส่วน TC-DASH-03 ล้ม 4 จาก 5 รอบ (ข้อความ `Command token too long: 128` จากตัวอ่าน PDF `pdf-parse` 1.1.1) และ TC-WORKFLOW-03 ล้มครั้งเดียวในรอบที่ 4 สาเหตุที่ TC-DASH-03 ผ่านได้บางรอบยังไม่รู้ และยังไม่ได้ตรวจว่า PDF แดชบอร์ดของเว็บ C ผิดมาตรฐานหรือแค่ตัวอ่านเก่า — ตัวเลข 48 ในตารางจึงเป็นค่าที่พบบ่อยที่สุด ไม่ใช่ค่าแน่นอน
- เซลล์อื่นรันครั้งเดียว ไม่ได้วัดช่วงความแกว่ง
- ยืนยันแล้วว่าเว็บและชุดเทสต์ของทั้งสามแบบสร้างและรันผ่านจากโฟลเดอร์ที่อยู่ใน repo นี้ (B 51/51 · C 51/51 · A 51/51 กับเว็บของตัวเอง ผ่าน `judge-harness/xjudge.sh`)
